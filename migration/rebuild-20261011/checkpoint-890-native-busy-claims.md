# Checkpoint 890: native Busy component claim/ready persistence

Baseline: c74be707fede984dbe0df4aea96e67bfb2ee462a (checkpoint 889). Eight production files and two test files are frozen in .runtime/busy-claims-final-sha256.txt. No schema, facade export, ingress payload, claim key, ready marker, response authority or receipt domain changes are introduced.

## Scope and identity

RuntimeCommandExecutor constructs one NativeBusyClaimOwner and retains it across all interactionServices calls. The installed ordinary Busy path and Busy ConfirmationOnly read opt in; default/direct helpers retain compatibility behavior. Checkpoint 888 confirmation receipt persistence and checkpoint 889 standard claims are unchanged. Checkpoint 882 Steer origin ownership remains shared with ordinary Steer.

Before the first asynchronous step, the owner captures the decoder-minted routed work, exact raw custom ID, original interaction/ingress/application identity, actor, channel, nullable source message, action and serialized pre-ACK Busy choice. The custody database must match the pinned owner path and the ingress key must match the interaction ID. The parsed component, routed component and exact raw custom ID must agree. Actor/channel and choice ID must match the original choice snapshot. No current database row replaces the action's pre-ACK snapshot. Request and response echo every captured primitive plus operation UUID, database path, timestamp, expiry and actor-bound ready marker. Each native envelope is bounded to 512 KiB, with a 384 KiB serialized-choice bound and 400-byte raw custom-ID bound. These are transfer limits, not SQL row, native memory or latency limits.

Only a confirmed non-Queue ExecuteAction acknowledgement mints a frozen, private, one-use completion handle. Copies, forged records, cross-owner handles and consumed handles cannot write ready or release. The handle proves the original claim persistence only; it does not authorize an app-server action. Source-message null is preserved rather than substituted with a prompt or click identity.

## Busy-specific operation sequence

Non-Queue Claim preserves the separate ready read, Busy state read, single-statement autocommit claim, and conditional second ready read. The Busy state read still decodes the entire row before expiry filtering, distinguishes claimed_at NULL from zero, and never deletes expired choices. It checks claimed/expiry state without refreshing the original choice. Claim remains the original UPDATE on choice ID, claimed_at IS NULL and expires_at > now. Release remains the original single-statement autocommit UPDATE to NULL. Existing-only helpers share their SQL bodies with compatibility helpers and perform a separate DEFERRED current-catalog check that ends before the original read/autocommit operation. They never create, migrate or repair a database.

Queue uses only ReadReady in this owner. Its existing native atomic admitBusyQueue transaction still owns exact choice/route validation, claim, prompt intake, canonical prompt owner and ready receipt. Queue cannot receive a NativeBusyClaim or invoke an owned Ready/Release completion. A lost Queue acceptance acknowledgement leaves that existing atomic ownership intact; a later confirmed ready read does not readmit or process its prompt again. Canonical Queue repeats retain prompt-owned confirmation eligibility; non-Queue canonical repeats remain on their existing manual-review path.

Ready persistence happens only after a successful Ignore, Stop or Steer action. It reuses claimComponentExisting's original IMMEDIATE expiry-cleanup/insert transaction and 1800-second ready TTL. The cleanup is intentionally unbounded in affected rows; a 6000-row fixture verifies it is not truncated to transfer-envelope capacity. A failed insert rolls the cleanup back. Successful action and durable result custody still precede Discord success delivery, receipt persistence and source-message clearing. Queue's result-recorded ingress stays prompt-owned; non-Queue stays completed. ConfirmationOnly reads only ready, never Busy state, claim or action.

Existing action policy is preserved: Pro Steer is rejected before claim, allowSteer=false remains presentation rather than a new veto, current route checks remain in Queue/control verification, and exact pre-ACK prompt/target remain action inputs. Definite owned error variants alone authorize Release. Unknown app-server outcomes and NativeSteerOriginUnknownError retain the claim. A native Claim or Release uncertainty is Store failure, never ControlNotDispatched. Ready uncertainty remains the existing known-completed-action Confirmation/Recovery failure; the interaction processor records action_completed and never runs the action again.

## Unknown outcomes and ownership

New Claim, Queue ReadReady, ConfirmationOnly ReadReady and RecoverReady use zero-queue Control admission. Already-owned Ready and Release use the existing finite Control completion FIFO, including while the same owner has another claim in flight. Per-operation slots do not expand the global Control1 capacity. Every submitted operation joins real native exit before its promise settles; timeout/cancellation never terminates an active database worker, releases custody early or treats a late commit as rollback. Close aborts and joins all owned operations. A proven synchronous pre-submit refusal preserves the unused handle. Asynchronous completion attempts remain one-use and conservative because the shared slot does not provide positive no-submission evidence for every FIFO refusal/cancellation.

Any admitted unknown/crossed/partial/late Claim, Ready or Release sets a shared runtime-local unresolved barrier. It survives repeated interactionServices construction, actual tested rollback and TTL expiry. New actions cannot claim through that owner. An explicit new click may recover only the same application's original actor/channel/source/raw-custom-ID/full-choice snapshot; the new interaction/ingress IDs are bound to the recovery request but do not need to equal the prior click. Recovery only reads the original durable ready marker. A live marker permits confirmation; absent ready returns ActionUnconfirmed without claim, cleanup or release. Different action, source, application or choice snapshot is blocked. Successful ready recovery does not clear the barrier. ReadReady/RecoverReady failures cannot mutate state and do not create new mutation authority. This is not restart/crash reconciliation.
