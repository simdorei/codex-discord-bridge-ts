## Scope and original authority

NativeCompletionReceiptStore admits two additional exact domains: component/confirmation/v1 and component/busy-confirmation/v1. Each requires the original null delivery guard and chunk index zero. Guarded completion domains and reserve/start-failure retain their existing validation. Arbitrary unguarded domains and async-question, publication-consent and abandonment confirmations are not admitted by this native profile.

RuntimeCommandExecutor.interactionServices explicitly opts in when it builds the ordinary handler. The handler passes that immutable choice to PreparedOrdinaryComponentConfirmation, which enables it only for the two exact completed-action plan domains. The prepared object retains the original factory-minted frozen plan; a copied plan cannot acquire authority. It owns only lazy confirmation/clear delivery and has no action callback. Async-question and recovery plans keep their existing compatibility delivery and abandonment timeout behavior.

The interaction processor still commits its completed-action custody outcome before invoking delivery. A failed outcome commit starts neither a native success receipt nor success confirmation or component clearing. Its original truthful ERROR-notification path remains available. Repeated prepared delivery and confirmed-plan recovery do not execute the action again.

Direct handler and delivery-helper callers keep the default compatibility profile, including implicit database initialization and the existing nonzero u64 Discord identity range. The native profile requires an existing database/catalog and a positive i64 channel. The source message is independently validated as a nonzero u64 PATCH destination, so an upper-u64 source message remains supported with an ordinary native channel. No global compatibility range is narrowed.

## Receipt, cancellation and ownership boundaries

The existing sendReceiptChunk wrapper and sendReceiptChunkWithPersistence state machine remain unchanged. They capture the exact serialized [channel, domain, logicalKey, 0] key, content SHA-256 and stable enforced nonce from the original plan. The worker retains the original BEGIN IMMEDIATE intent transaction and a separate BEGIN IMMEDIATE acceptance confirmation. Confirmed delivery must be durable before the exact components-only PATCH starts. A delivered retry performs only PATCH, and an absent source message requires no PATCH.

Unknown begin outcomes, changed content, unknown transport outcomes and failed receipt confirmation never authorize a repeated POST. A definite rejection blocks the original receipt; an owned validated 429 rejection uses the existing separate release transaction and permits only the existing later explicit receipt retry. The HTTP client's existing in-flight wire429 retry remains unchanged and reuses the exact nonce/body within the same original intent. Block retains its original single-statement autocommit semantics.

An accepted HTTP message is confirmed even when caller cancellation occurred during transport. The caller may then stop before PATCH. Native receipt timeouts/cancellation retain ownership through actual SQLite worker exit; a late possible commit remains unconfirmed to the caller. There is no main-thread storage fallback or detached mutation. Begin keeps the existing zero-queue Control admission, and already-owned Confirm/Release/Block use the existing finite completion FIFO. Locks do not block main-thread timer progress, and no capacity is released before native exit.
