Every request and successful acknowledgement carries the operation UUID, database, original click primitives, exact canonical full seal and displayed-proposal bytes, and host timestamp. These transport limits do not establish SQLite memory, SQL-work, throughput, or Windows qualification.

All Read, Ingress, Decide, and Recover operations use zero-queue Control admission. An existing read handle is never completion-FIFO authority. Admission, Control capacity, and any acquired original target lease remain owned until actual worker exit, including timeout, cancellation, owner close, and late native completion. There is no new pool, main-thread fallback, worker termination, or automatic retry loop.

An admitted decision without an exact joined acknowledgement establishes one shared runtime-local uncertainty barrier across both flows. The handler uses an unconfirmed-result classification, never claims that the decision was not recorded, and logs rather than issuing a misleading success/error confirmation. No new decision or hold release is authorized. A subsequent explicit installed prepareComponent invocation can recover only the exact original decoded click, canonical database, and a still-live admission. Capture compares all original identity primitives and returns only the retained private Unknown handle; the handler takes its original sealed target lock and performs Recover only, with no repeated authorization reads or decision submission. There is no automatic retry within the failed call. Explicit recovery performs a read-only receipt check. A missing receipt remains uncertain. A recovered receipt does not clear the shared barrier or create fresh mutation permission. This is not crash/restart reconciliation. Ordinary Discord redelivery remains a duplicate at the claim cache or ingress admission; a new click has a different interaction ID and is refused by the barrier. After the normal worker fails, its ingress remains held and its original admission is released. Reusing that released work cannot enter the helper. A caller that deliberately retained a live admission clone may prepare the exact receipt display, but that does not repair held ExecutionCustody, record action completion, or release any hold. ## Store order and transaction boundaries

The installed order remains first delivered-proposal authorization read → shared original-target lock → repeated authorization read → separate existing-only ingress read → original IMMEDIATE decision transaction → lazy display confirmation. Pre-ACK recovery routing, proposal production/delivery, and broad ExecutionCustody persistence remain on their compatibility paths and are outside this slice. No source read is fused with a later scope, and missing stores or incomplete schemas are never created, initialized, migrated, or repaired.

The initialized compatibility publication API and the new existing-only native API share the same transaction body. The abandonment compatibility path remains existing-only. Native helpers additionally compare the exact originally captured click, displayed proposal, and complete canonical seal inside IMMEDIATE before any write, and recheck them before committing a new decision. This transaction binding is independent of transport acknowledgement equality.

Publication preserves its original intent-only semantics: Pending stays present, no request starts, and no existing hold is released. An exact original completed replay may observe its receipt after expiry and evidence drift. A fresh interaction with the same choice must still have live unowned execution custody and fresh evidence, and it can only observe the original immutable decision. A conflicting choice cannot overwrite it.

Abandonment preserves exact consumed-interaction identity. A fresh interaction cannot reuse another click's receipt. AbandonOnly atomically records the decision and exact cancellation tombstone, verifies the original Pending row and unaffected context, removes only that exact Pending row, and rechecks the tombstone, queue absence, retained seal, revision, click, and unaffected context. KeepHeld removes no row. Explicit read-only recovery also verifies the exact tombstone and absence of executable queue state.
