# Checkpoint 889: native standard component claim/ready persistence

2026-10-15 UTC. Installed bound approval/input handling now uses an existing-only native claim owner. Migration and live-runtime qualification remain incomplete.

Baseline: 89fc4bf0758d0d0c667780b0e674212d0207c481 (checkpoint 888). Eight production files and two test files are frozen in .runtime/standard-claims-final-sha256.txt. No schema, facade export, ingress payload, claim-key format, response authority or receipt-domain change is introduced.

## Scope and original identity

RuntimeCommandExecutor owns one NativeStandardClaimOwner and shares it across interactionServices instances. Only the standard BoundApproval/BoundInput branch opts in. Busy choice-state/claim/resolve/ready handling is deliberately deferred because its ownership and transaction sequence differ. Async-question, recovery, direct standard-helper and default ordinary-handler callers retain their compatibility behavior. Checkpoint 888 confirmation receipt persistence and delivery ordering are unchanged.

The decoder-minted routed work retains its original custom_id in a private WeakMap. A read-only accessor returns it only for that original routed object. No enumerable/serialized work or ingress field is added. Before the first native await, the owner captures the original interaction ingress ID, interaction ID, application ID, actor, channel, source message and exact bound custom ID. The ingress ID must match the interaction ID; work, component and custom ID must agree; the custody database must match the pinned owner path. Nonzero u64 identities retain the original standard-helper range. Actual ingress admission and native confirmation receipts retain their own existing range policies.

The canonical action claim remains actor-v1 plus the original persistent component key, actor and channel; alternate answers for the same prompt intentionally share it. The ready marker and confirmation plan algorithms are unchanged. Worker requests and ACKs bind every captured field, operation UUID, pinned database path, timestamp, expiry, action claim and ready marker. Both request and reply have 64 KiB envelope bounds. Only an exact confirmed ExecuteAction ACK mints a frozen private one-use handle; copied, forged, cross-owner and consumed handles cannot ready or release a claim. The generic factory-minted confirmation plan remains display-only and is returned only after the action succeeds or a durable ready marker is confirmed.

## Source transaction and action boundaries

Claim runs the original ready read, then the original BEGIN IMMEDIATE expiration cleanup plus INSERT OR IGNORE plus commit, then a separate ready read only if the action claim was already present. A ready marker is written by a later, separate original claim transaction. Release retains the original single DELETE autocommit operation. The SQL bodies are shared with the compatibility functions.

Native claim transactions verify the current catalog inside their IMMEDIATE transaction. Ready reads and releases perform a separate DEFERRED catalog-verification snapshot that ends before their original autocommit statement. Existing-only opens never create, initialize, migrate or repair a database. The expiration-cleanup DELETE remains unbounded in affected rows, as in the source; envelope/capacity bounds do not bound SQL work, native memory or latency.

After confirmed Claim, standard handling still selects the exact pending request occurrence and generation, verifies original prompt/turn ownership and actor/channel, then calls the same borrowed PortableResidentLifecycle.respond boundary. No synchronous authority hook was replaced by an awaited worker result. A claim is persistence evidence, not permission to respond. Pre-response construction/authority failures release only that original privately owned claim. Post-response failures use the unchanged concrete owned app-server error allowlist; unknown/closed/indeterminate failures retain it. No arbitrary error label or copied record can authorize release.

The action completes before ready persistence. Ready failure is still the existing known-completed-action Recovery error, so the interaction processor records completed-action custody and follows its existing notification policy. The processor must commit completed-action custody before any success receipt/confirmation/clear starts. Successful prepared delivery remains incapable of reexecuting an action.

## Unknown outcomes and ownership

Claim and read-only recovery use zero-queue Control admission. Already-owned Ready/Release uses the existing finite Control completion FIFO, including when a different claim is active in the same owner. Per-operation slots add no capacity to the global Control1 budget. Every path joins actual native exit before releasing the operation, caller custody or capacity. Cancellation/deadlines do not terminate a database worker or interpret a late commit as rollback. Close aborts and joins all owned operations. A proven synchronous pre-submit refusal preserves the original handle. An asynchronous completion attempt remains one-use and conservative: the shared slot does not supply a positive no-submission receipt for every FIFO refusal/cancellation, so such uncertainty does not authorize release or automatic retry.

Any admitted unknown/crossed/malformed/late/cancelled Claim, Ready or Release acknowledgement establishes one bounded runtime-local unresolved barrier. No new action claim is created after that uncertainty, including after the persistent claim TTL expires or a tested SQL transaction actually rolled back. An explicit later click may only read the original ready marker when the canonical action/actor/channel/source and application match. Its interaction/ingress ID and exact answer may differ because it is a new click on the same canonical prompt. A live ready marker permits confirmation only; absent ready returns ActionUnconfirmed without cleanup or insertion. Other identities remain blocked. The barrier is intentionally not cleared by successful ready recovery. It is not restart/crash reconciliation.
