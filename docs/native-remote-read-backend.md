Status: WIP. Final independent review is unverified; this candidate is not approved for promotion.

This slice adds real temporary-filesystem read/list execution behind the 910 typed project ports. It remains an explicit, uninstalled local capability factory. The CLI/default application's remote configuration is still rejected, and the 912 synthetic profile does not become production-approved. There is no native write, checkpoint, command, Git, image, terminal or computer implementation here. Their operation ports remain absent and dispatch returns the existing `projectcapability` error rather than a success result.

Reads reuse the existing 1 MiB bound, original-byte SHA-256, strict UTF-8 decoding, BOM preservation, Rust-style line selection, 1..500 clamping and redaction worker. Valid UTF-8 containing NUL is retained; a binary-looking extension alone does not reject a file. Invalid UTF-8 is `projectfileencoding`, excessive size is `projectfilesize`, invalid path/pattern is `unsafeprojectpath`, and ordinary missing-file/native I/O is `projectfile`. Native OS error text is platform-specific, rather than an exact Rust diagnostic claim. Original typed file failures keep their immutable captured classification and redacting output boundary.

Listing keeps source directory exclusions and sensitive-path policy, UTF-8-byte glob matching, case-sensitive POSIX patterns, lowercase-then-original UTF-8 ordering, per-file single-link regular-file qualification, skipped unreadable candidates, 1..500 result clamping and truncation only when more successfully opened matching files exist. Metadata sizes remain bigint. Files larger than the read limit can appear in a listing without reading their bytes.

Source `relative_text` display behavior is preserved: a literal POSIX backslash filename is opened by its original native spelling while its output path replaces backslashes with slashes. Display paths are not canonical native identities and distinct native names can therefore share an output spelling. This slice does not deduplicate those distinct source-native paths by display text. As in Rust, native colon/backslash filenames can appear in listings even when the separate user-supplied read-path policy refuses that spelling; listing never reopens their normalized display path.

## Authority and ownership

`createRemoteNativeReadFactory` accepts a passive allowlist of 1..16 thread IDs and actual, already-bound `RemoteReadOwner` objects. All entries, identities and duplicates are checked before any transfer. It performs no root acquisition from an incoming command or binding. A private runtime acquisition receipt also prevents the erased TypeScript constructor from being used to fabricate an owner from a path/handle-shaped object. A granted reader is transferred once into an authentic private native-read capability; subsequent direct reads, close calls or transfers through the original reader are rejected. Existing root spelling, canonical identity and explicit initial root-symlink behavior are retained.

The captured canonical root and thread ID must match an incoming binding exactly. Relative roots, aliases, changed thread IDs, forged owners, proxies and getters cannot mint a capability. Input-array or entry mutation after capture has no effect. Root identity is checked again during actual native operations; lending a previously acquired capability does not refresh its root identity or acquire a replacement directory.

Each backend borrows that captured capability. It owns its accepted read/list promises and exact read-session identity. Read-only sessions allocate no terminal/UI resource and expose no terminal/UI operation port. The existing dispatcher continues to own connection/session authentication, deadlines, binding expiry, replacement ordering, mutation rejection and result serialization. Its exact immutable binding object and a live issued session identity are required at the backend boundary. These ports are internal ownership contracts, not a second protocol decoder or an authenticated user-permission enrollment mechanism.

Closing a backend aborts and joins all its accepted native/CPU operations. It does not close the grant while another replacement backend still borrows it. Connection retirement/reconnect retains the grant under the existing dispatcher. The normal local shutdown order is to dispose the factory after closing its dispatcher; factory disposal also independently stops/joins all remaining backends before closing the native owners. There is one idempotent disposal receipt. A clean factory-first disposal also preserves confirmed cleanup when the dispatcher subsequently shuts down. Disposal never retries a failed native close or reports an uncertain cleanup as successful.

A failed root FileHandle, per-operation FileHandle or directory-stream close retains the resource and error, blocks further native admission and transfer, and makes session/backend close and final factory disposal fail. The dispatcher receives that failure and blocks reconnect; factory disposal still attempts every owned native close after any backend close failure. Already accepted work remains bounded and joins normally. The failure latch prevents repeated new operations from accumulating an unbounded retained-resource set.

## Cancellation and limits

- No new worker pool or queue. The existing reader CPU slot and shared Background budget remain in use. Native filesystem operations use the existing asynchronous Node APIs. The outer dispatcher/connection queue is unchanged.
- At most four read/list operations are accepted by a factory and at most twenty borrowed backend owners are retained (sixteen projects plus four in-flight replacements). Saturation rejects immediately. Read rendering retains its existing one-active, zero-queue policy.
- Reads retain the existing 256-component and 1 MiB bounds. Listing counts at most 10,000 entries, including excluded entries; exceeding the scan limit rejects the entire operation. It also refuses more than 4 MiB of cumulative filename/path text or 8,000,000 conservatively charged glob cells. These are intentional bounded-profile restrictions beyond Rust's synchronous helper, not partial success or exhaustive large-repository compatibility.
- Directory streams buffer 32 entries and use a lossless Latin1 byte bridge before strict UTF-8 decoding. Invalid native UTF-8 names reject the whole listing instead of opening a replacement-character alias. Rust's lossy display of those names is outside this qualification.
- Scans hold bounded descriptors: ancestor directory handles plus at most one current 256-component validation chain, rather than one retained full chain at every depth. The 256-component limit bounds recursive depth; directory and file handles are joined on all exits. These are logical ownership limits, not an RSS, throughput or filesystem-latency certification.
- Standard AbortSignal instances are checked through captured intrinsic brand/cancellation methods; public method/property overrides, accessor fields, subclasses and proxies are rejected before native admission or deadline timer creation. The combined owned signal is created before its timer is armed. This accepts ordinary Node signals, not arbitrary modifications to Node internal signal state.
- A captured monotonic budget controls a per-operation cancellation timer. External cancellation, retirement and disposal stop future steps; every already accepted filesystem call and close is awaited. Pure rendering is terminated and joined through the existing worker slot. No timeout race returns early and releases native custody.
- Expired/cancelled budget failures have an authentic constructor receipt, so mutable error fields or forged error prototypes cannot choose `request_expired`/`request_cancelled`. Ordinary file failures still use the existing redacting mapper. The asynchronous deadline/cancellation checks are an explicit TS ownership extension to Rust's synchronous list/read branches.
