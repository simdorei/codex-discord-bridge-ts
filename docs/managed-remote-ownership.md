# Managed remote ownership foundation (911)

This is a complete synthetic/offline-qualified managed ownership slice. It does not enable the runtime root or CLI remote branch. `SyntheticManagedRemote` explicitly accepts only a literal `ws://127.0.0.1:<port>` destination and a supplied `synthetic-` token. Tests open only local fixture listeners. There is no environment or credential lookup, operational connection, TLS relaxation, native filesystem/UI/terminal implementation, or production protected persistence.

## Concrete ownership

`prepareManagedRemoteAgent` passively captures configuration, clock/backend functions, diagnostics, token wrapper, status/control and synthetic handoff functions before its first await. Managed handoff/diagnostic functions run with an undefined receiver; no callback receives the managed state, token wrapper or dispatcher through JavaScript `this`. The dispatcher likewise detaches its configured factory/clock functions. Existing leaf methods retain only their captured public port-record receiver, without hidden owner authority. Preparation atomically claims the underlying shared status/control states, including all clones, for one managed lifetime. The claim is never recycled after failure or close. A rejected combination does not consume the other unused state. Callers can still observe status and explicitly request the shared sticky control; those objects are diagnostic/control contracts, not project/session authority.

Preparation owns one real `RemoteProjectDispatcher`, restores once, validates and freezes binding metadata, and sequentially installs bindings through its actual `upsert`. Only then can the authentic prepared receipt run. There is no catch-all execute callback. Copied, proxied, foreign, already-running, closed or failed receipts cannot run another lifetime. Unused prepared resources can be closed with an idempotent completion receipt. Partial restore failure closes all already accepted resources before rejecting; failed cleanup retains an inspectable authentic owner in `ManagedRemoteOwnershipRetainedError`, with no automatic retry.

Each reconnect creates an attempt-specific adapter bound to the same dispatcher. The adapter holds the exact receipt minted by `beginConnection`; generation numbers never substitute for receipt identity. Concurrent adapters cannot claim the same dispatcher. Failed begin cannot retire a different attempt; duplicate retirement shares its real completion/failure promise. Prior-attempt execute/retire callbacks cannot affect a subsequent receipt. The managed loop additionally retains the attempt until the existing `connectAndServeRemote` has joined command work, retired sessions and disposed the actual socket. No reconnect begins before that settlement. Cleanup failure stops retrying a faulted dispatcher.

The existing native connection, hello/ack, sequential reconnect loop, native codecs, four-active/sixteen-total command workers and command-byte accounting remain authoritative. There is no new queue, pool, replay mechanism or fallback executor. Successful cached mutations survive reconnect on the same bound project, but each new connection still requires session acknowledgement. Volatile-cache and uncertain-effect limitations from 910 remain unchanged.

## Binding handoff boundary

The source sticky restart flag is sampled once after the loop and actual connection/session cleanup return. A request made during command/session drain counts. The root must read its owned restart marker and request this control before shutdown; a request made only after the sampling boundary or remote completion cannot retroactively persist anything.

The dispatcher then exports only immutable `threadId`, `root`, `expiresAt` metadata, filters expiry against its current clock, and sorts by Rust UTF-8 thread-ID order. No session identities, connection generations, cache, command/result queue or uncertain mutation outcome crosses the boundary. Empty output skips preparation. Final project cleanup is joined before the captured synthetic protect port runs; expiry is re-filtered using the captured clock immediately before protection, so a slow cleanup cannot persist stale bindings. This explicit asynchronous cleanup ordering is a TS safety adaptation; failed cleanup prevents protection. Protect failure propagates after resources have been joined. Cancellation never treats signal delivery as a cleanup/persistence completion receipt.

The restore boundary rejects duplicate bindings and more than 16 projects before acquiring any project resource, matching the stricter 910 in-memory cap. It validates immutable DTO graphs with a 1,048,576 aggregate string/key-unit budget, plus each identity/path's 4,096-unit budget. This is not Rust's 1 MiB serialized envelope byte limit or a heap/RSS guarantee. Trusted fixture/backend functions must settle actual accepted work and own partial initialization on rejection; this boundary cannot certify the correctness of caller implementations.

## Deliberately missing native handoff

`SyntheticProtectedBindingPorts` is a named fixture boundary, not encryption or durable storage. It implements none of Rust's format-1/protocol-10 envelope, exact gateway/device fingerprint, 120-second resume window, 128-project native handoff limit, canonical-directory validation, claim-by-rename, claimed-file removal, current-user Windows protection, sync/atomic replacement or protected read/write backend. Rust's system protector is unavailable on unsupported platforms; there is no plaintext fallback here. Synthetic callbacks do not establish native protection, filesystem confinement, account authorization or persistent restore parity.

Root work remains separate: prepare/restore before gateway opening; shared status supplied to Pro; source-ordered typed ingress, interaction, remote-MCP, supervisor, heartbeat, completion; monitored remote exit and partial-startup join; restart-marker/control sampling before requestStop; and singleton exclusion held through all real cleanup. No such root startup/singleton claims are made by this slice. CLI rejection, final wire/schema authority and inactive 893 are unchanged.
