# Retained-cutoff bootstrap read-work measurement

Checkpoint 935 measures one synthetic pending-startup recovery through the original production bootstrap coordinator and native workers. It changes no production module. Checkpoint 922 measured warm polling and explicitly excluded bootstrap IO; this experiment addresses only that separate read-work boundary.

## Frozen profile, declared before execution

One temporary SQLite store, target/channel and rollout. Exactly 16,384 LF-terminated JSON records, each 256 UTF-8 bytes, total N = 4,194,304. The first and last historical records carry turn contexts; the middle 16,382 carry unique historical messages. Prepare schemas/mapping, capture authentic EOF N and retain the original pending operation before appending one 256-byte record carrying a different turn context. Setup and verification are unmeasured.

Context limits: maxBytes 4,194,304; maxRecords 16,384; maxRecordBytes 512; maxWindowBytes 65,536; maxTurnBytes 16,384; native timeout 5,000 ms. Coordinator deadline 10,000 ms; test safety timeout 60,000 ms. Deadlines are guards, not latency acceptance. Expected submissions, in order: ReadTarget, RecoverContext, CompleteContext. No Capture, Retain, later EOF recapture, receipt adapter or transport adapter submission is allowed in the measured interval.

The result must be Resumed, unreconciled, with the original operation ID/time and retained offset N, cursor revision 1, historical final turn retained and pending intent retired. The successful original recovery response must report exactly 16,384 scanned records and N logical bytes. Its sampled anchor sees file size N + 256 but retains offset N. The appended turn must not replace the historical turn. Real verification reads must find the exact cursor and no pending intent or receipt rows.

## Source-derived actual returned-byte accounting

The expected ranges are frozen independently of execution from startup-context-scan.ts, continuity-observation.ts, file-window.ts and startup-intent-recovery-native.ts:

- ReadTarget: zero rollout reads or opens.
- RecoverContext: read 256-byte tail [N−256,N), then 256-byte prefix [0,256). Scan 64 contiguous 65,536-byte payload windows covering [0,N), in order. The final verifyCurrent opens the file for metadata only and returns no payload bytes. Total: N payload bytes + 512 anchor bytes; 67 opens and 67 completed closes.
- CompleteContext: reread the 256-byte tail and 256-byte prefix at the same offsets. Total: 512 anchor bytes; two opens and two completed closes.
- Total actual returned rollout bytes: 4,195,328, comprising 4,194,304 payload bytes and 1,024 continuity/boundary reread bytes. Total opens/closes: 69/69. Logical scanned bytes remain N; anchor rereads must not disappear into that logical counter.

Each actual FileHandle.read result is reconciled against these ordered ranges, including position, remaining requested length and positive returned count. Short reads may split a range, so read-call count is an observed value rather than a fixed acceptance constant. Metadata-only operations do not count as returned bytes. No observed range may include the appended record.

## Transparent native-isolate observer

The explicit frozen test-process argv loads the test observer with --import at genuine process startup. Original native workers inherit that startup preload. No Worker constructor or runtime execArgv mutation is used. The preload is inert for setup and regression workers without the scoped observer environment-data entry. The real production worker module URL, workerData, cancellation buffer, timeouts, signal, native ACK protocol and original results remain unchanged. The test does not replace workers, fake SQL/decoder results, or infer IO from scannedBytes.

The preload wraps exact-rollout fs/promises.open results inside each worker, forwarding FileHandle.read and close with their original receiver, arguments, return values and errors. It records only numeric metadata into a separate SharedArrayBuffer; it never reads or parses source bytes itself and never emits extra ACK messages. A ready marker and actual native thread ID witness preload execution; exact nonempty real read ranges witness that interception reached the filesystem binding production uses. The observer restores main-isolate run/environment state and worker fs bindings. Original worker exit must be witnessed, successful opens and closes balanced, and both handle count and the production active-file-read counter zero at exit. All main-isolate worker lanes and active-file-read count must also be zero after native join and cleanup.

Telemetry has a fixed 1,024-read capacity per worker. Overflow, invalid telemetry, failed reads/closes, missing preload, missing response, missing exit, missing ranges or extra ranges fail acceptance. Actual read counts and incomplete observations survive failure. Summary output occurs after owner and temporary-resource cleanup; failures retain their stage and observed numeric telemetry without claiming committed progress. Raw error text, paths, packets, database files and rollout/message bodies remain out of the bounded public summary.

The coordinator has no transport argument or call surface. This slice checks the exact worker submissions and zero durable receipts, rather than pretending to observe a transport counter on a transport that was never installed.

## Evidence limits

This is bounded synthetic retained-cutoff bootstrap read-work evidence only. Actual returned bytes are not physical cold-cache IO, cache misses, storage traffic, SQL volume, throughput, memory/RSS or latency qualification. Sampled anchors do not prove unseen historical integrity or filesystem/SQLite atomicity. It does not establish a Rust performance comparison, full G1/G7, native Windows behavior, full restart/corruption/fairness matrices, live Discord correctness, deployment readiness or migration PASS.
